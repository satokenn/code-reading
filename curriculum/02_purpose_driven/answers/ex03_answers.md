## 問2 — スタート地点の特定

`pyproject.toml` の `[project.scripts]` セクションを確認します：

```toml
[project.scripts]
flask = "flask.cli:main"
```

つまり `flask run` は `src/flask/cli.py` の `main()` 関数から始まります。

---

## 問3 — 読む・飛ばすの判断例

| 要素 | 判断 | 理由 |
|---|---|---|
| `import` 文 | **飛ばす** | 依存関係の詳細より「run コマンドがどこにあるか」が目的 |
| `@click.group()` のデコレータ定義 | **飛ばす** | Clickの設定は今日の目的には関係ない |
| `run_command()` 関数のシグネチャ | **読む** | 「flask run」= `run_command` のはずなので直接関係する |
| `run_command()` の内部実装 | **読む(部分的)** | サーバーの起動処理があるはずなので、起動に関係する部分だけ |
| エラーハンドリングのtry/except | **飛ばす** | 正常系の起動フローを追うのが目的 |
| `click.option()` の各オプション | **飛ばす** | オプションの詳細より起動フローが目的 |
| `_validate_key()` などのヘルパー | **飛ばす** | バリデーション処理は起動フローの本流ではない |

## 問4 — フロー図の例

```
[flask run コマンド実行]
        ↓
[1. pyproject.toml の flask.cli:main が呼ばれる]
        ↓
[2. cli.py の main() → click グループ が起動]
        ↓
[3. run_command() が呼ばれる]
        ↓
[4. [不明: 推測] app ファクトリ関数が呼ばれて Flask アプリが生成される]
        ↓
[5. [不明: 推測] Werkzeug の開発サーバーが起動する]
   （app.run() または run_simple() 相当）
        ↓
[N. 開発サーバーがリクエスト待ち状態になる]
```

> 「不明: 推測」と書いた箇所は、インターフェースだけでは判断できなかった部分です。  
> これが **能力Ⅲ（抽象の漏れ）** の候補になります。

## 問5 — 読み飛ばし率の目安

Flaskの `cli.py` は約500行あります。

`flask run` の起動フローを追うために実際に読む必要があるのは：
- `run_command` 関数本体（約40〜50行）
- `main()` 関数（数行）

**読んだ量: 約50行 / 全体500行 = 10%**  
**読み飛ばし率: 約90%**

このように、明確な目的があれば全体の10%以下しか読まずに目的を達成できます。

---

## 振り返りのポイント

読み飛ばし率が低かった（よく読みすぎた）場合の典型的な原因：

1. 目的が曖昧 → 「この関数も関係あるかも」と判断できない
2. 知らない関数名が不安 → 全部確認したくなる
3. click/Werkzeug などのライブラリへの知識不足 → 信頼できずに実装を追ってしまう

**3番目は能力Ⅰ（抽象化の信頼）の訓練が効く**部分です。ライブラリのシグネチャを信頼できるようになると、読み飛ばし率が上がります。
